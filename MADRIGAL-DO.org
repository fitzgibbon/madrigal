#+TITLE: Madrigal Do Implementation Plan

* Goals

- Add =madrigal-do= for one-shot, prompt-driven Emacs actions.
- Add =madrigal-do-dwim= to propose likely actions through minibuffer completion and execute the selected instruction through the same path as =madrigal-do=.
- Keep actions stateless across invocations: no conversational buffer and no previous action history in model context.
- Capture focused actions as plists with a live buffer, optional window, optional point-local buffer context, and optional project.
- Store action and tool lifecycle data in bounded Lisp records rather than Org text.
- Allow Madrigal sessions and actions outside projects while including project information when available.
- Reduce the eager eval-tool prompt by moving runtime and package information behind bounded reflection functions.
- Improve existing Org-session responsiveness by caching and debouncing context work.
- Give assistant and focused-action agents a persistent reusable Emacs Lisp library.

* Current implementation status

- Added optional project discovery and non-project Org sessions.
- Added project context to existing session requests.
- Added bounded plist focus contexts containing buffer, cursor, region, window, and optional project data.
- Eval calls re-enter the captured buffer and live window at tracked point/mark markers, even after the user moves focus or edits preceding text.
- Added UI-independent eval event sinks while preserving Org rendering.
- Added =madrigal-do= with 1000-item default retention for Lisp action, turn, tool, and tool-result records.
- Added tool-free =madrigal-do-dwim= suggestions using a compact sum-of-products JSON schema. Selected immediate actions execute one validated eval invocation directly; prompts and custom input use the shared executor.
- Added bounded reflection entry points, action self-introspection helpers, and a reduced eager eval-tool description.
- Added history/token caching and idle-delayed Org context refreshes.
- Added initial ERT coverage and user documentation.
- Added =persist-elisp=, which evaluates reusable agent code and stores it in one
  file beneath =user-emacs-directory=, loaded whenever Madrigal starts.
- Updated assistant and focused-action prompts to build and reuse that library.

Remaining work is recorded in the phase checklists below, particularly richer stale-suggestion handling, a fully typed controller execution context, broader reflection coverage, and architecture diagrams.

* Architecture

** Execution context

Use a validated execution context carrying the request id, origin buffer and marker, focus context, and event sink. Tool execution produces a structured event, and UI adapters decide whether to render it in Org or retain it in an action record.

** Focus context

Capture focus before opening a minibuffer. Use a validated plist with reserved =:origin= and =:project= entries. Nest major mode, minor modes, optional point, region, range, and text beneath =:origin :buffer-context=. Omit point for whole-buffer actions. Retain live Emacs objects internally and replace them with descriptive data before serialization.

** Project context

Normal interactive actions discover optional project metadata. Project action commands provide only project name, root, and backend, with no buffer, mode, window, point, or text context. Derive eval directories privately from the origin buffer or project root rather than adding them to model context.

** Action records

Use bounded =madrigal-action= and =madrigal-tool-event= structures for active and recent requests. Tool calls and results remain in the transient =llm= prompt while a request is active but are never included in a later action automatically.

** Commands

- =madrigal-do=: capture plist focus context, read an instruction, execute it.
- =madrigal-do-dwim=: capture focus, request ranked structured suggestions without tools, offer them through =completing-read=, and pass the selected or custom instruction to the same executor used by =madrigal-do=.
- =madrigal-do-project= and =madrigal-do-project-dwim=: run the corresponding command with project-only context.
- Add cancellation and inspection commands for active and recent actions.

** Prompt design

Use a minimal stable system prompt for execution. Mark captured editor content as data rather than instructions. The sole execution tool is Emacs Lisp eval. Final responses select either a brief echo-area string or a complete Org document shown read-only with =q= bound to quit. Suggestion generation receives the same focus context but no tools and cannot alter Emacs.

** Reflection

Provide bounded discovery for runtime details, packages, features, functions, variables, commands, key bindings, modes, project information, and focus-buffer slices. Search responses carry truncation and offset metadata. Avoid eagerly listing installed packages or all prelude documentation in the eval tool description.

** Existing Org sessions

Keep Org as the editable persistence format. Add concise working-directory/project context to each request. Separate eval execution from Org rendering. Cache parsed history and token information, mark it dirty on edits, and debounce expensive mode-line and compaction calculations.

* DONE Phase 9: immediate actions and prompt DWIM

** Decision

DWIM presents two kinds of suggestions:

- *Immediate actions* are concrete Emacs tool operations.  Selecting one performs
  its prepared tool action immediately against the captured focus context.  It does
  not create a =madrigal-do= action, request another model turn, or invoke the
  larger execution model.
- *Prompts* are questions, investigations, explanations, plans, or other advisory
  requests.  Selecting one starts a normal =madrigal-do= request with the captured
  focus context.

The suggestion response contains everything needed to run an immediate action or
to make a prompt.  Generation remains tool-free: no Emacs evaluation
occurs while candidates are being produced or while the menu is displayed.  User
selection is the authorization boundary for an immediate action.  Custom minibuffer
input is a normal =madrigal-do= request.

** User experience

- Present a small ranked menu in the original concise format.  Place ⚡ after the
  relevance circle for immediate actions and 🧠 for prompts.
- An action description states the operation and target.  Selecting it runs the
  operation directly, showing only its value on success or ❌ and the error on failure.
- A prompt states the question or investigation and launches the normal executor.
- Users may edit a prompt, enter custom text, or quit.  Edited and
  custom text is treated as an ordinary =madrigal-do= request.  An action candidate
  is selected as-is; editing it must not accidentally run stale prepared tool data.
- If the origin is stale or killed before selection, do not run an immediate action
  or launch a request; use the existing stale-origin handling.

** Data model and protocol

- Model each candidate as =relevance × ((description × tool call) + prompt)=.
- An action candidate carries a concise description and one validated, bounded
  direct tool call with arguments needed for the frozen focus context.  It carries
  no controller continuation, provider handle, or pending model turn.
- A prompt candidate carries the text supplied to =madrigal-do=.
- Validate alternative-specific fields, field bounds, duplicate text, and the direct
  invocation representation.  Discard malformed candidates independently and retain
  valid candidates.  Do not reinterpret tool calls or prose outside the schema.
- Keep suggestion diagnostics and immediate-action results bounded and separate from
  ordinary =madrigal-do= action history.

** Execution model

- Capture and freeze focus before requesting suggestions.
- Request suggestions without tools.  The response may describe a direct action but
  cannot execute it.
- For a selected action, revalidate that the origin and invocation are still valid,
  then invoke the Emacs eval tool directly with the frozen context.  Render and
  retain the resulting tool event without creating a controller action.
- For a selected prompt, call the existing =madrigal-do= executor with only its
  text and frozen focus context.
- Never route an immediate action through =madrigal-do=, a controller checkpoint,
  a provider continuation, or the larger execution model.

** Implementation plan

*** 1. Define the sum-of-products schema and validation

- Add records, normalization, and bounded diagnostics.
- Define the restricted direct-invocation representation and validate it before the
  menu is shown and again before execution.
- Keep prompts and action tool calls distinct so editing display text cannot execute
  prepared tool data.

*** 2. Generate and present suggestions

- Update the tool-free request to produce ranked immediate actions or prompts and
  no live tool calls.
- Add grouped completion display and annotations while retaining plain-text support.
- Preserve cancellation, occupied-minibuffer, stale-origin, and partial-invalid
  response handling.

*** 3. Execute selected immediate actions directly

- Add a direct tool-invocation path that restores the frozen focus context, invokes
  eval, and presents its value or error directly.
- Ensure it has no =madrigal-do= action record, controller state, execution-model
  request, or later model turn.
- Keep result retention, cancellation, and error reporting appropriate for a single
  immediate tool operation.

*** 4. Route prompts through the ordinary executor

- Pass a selected prompt and frozen context to =madrigal-do=.
- Treat edited prompts and custom input identically to ordinary typed requests.
- Do not pass action metadata or direct tool-call data to the
  execution model.

*** 5. Test and document

- Test parsing and validation for both categories, malformed invocations, duplicate
  candidates, and partial-valid responses.
- Test that generation and menu display make no eval call; selecting an action makes
  exactly one direct tool invocation and no =madrigal-do= request; selecting a prompt
  makes one ordinary request.
- Test edited/custom input, cancellation, stale origins, result presentation, and
  absence of execution-model traffic for immediate actions.
- Document the two categories, explicit-selection behavior, direct-action limits,
  and context/privacy rules.
