#+TITLE: Context Scopes for madrigal-do and madrigal-do-dwim
#+AUTHOR: Madrigal

* Decision

Make context scope an explicit, shared concept for =madrigal-do= and
=madrigal-do-dwim=.  With no prefix argument, both commands capture the
highest-scoring default-eligible local context.  With a prefix argument, they
open completion over every discovered context candidate before dispatch.  The
selected candidate is the sole context supplied to the request.

This replaces the timed widening carousel as the primary interaction. Completion
is visible, reversible, searchable, and does not dispatch merely because the
user pauses. A lightweight overlay may preview the highlighted candidate, but
RET in completion is the authorization boundary.

Project scope becomes a normal candidate rather than a separate command family.
A session candidate is also available for actions about Emacs itself; it
supplies no origin-buffer, region, project, or other document context.  Remove
=madrigal-do-project= and =madrigal-do-project-dwim=; project actions use scope
selection exclusively.

* User interface

** Default invocation

No prefix selects the initial candidate and dispatches normally:

- =madrigal-do= reads an instruction and sends it with the selected context.
- =madrigal-do-dwim= requests tool-free suggestions with that context, then shows
  its existing action/prompt completion UI.

A central relevance policy chooses the default from the complete candidate set.
An active region receives the strongest default signal.  Project and session
candidates are explicit-only; no local default selects them.

** Prefix invocation

A prefix opens a completion session before reading/dispatching the action. Its
entries show the provider-supplied label, discovery provider, character count,
relevance, and whether the candidate exceeds the model provider's known context
limit:

#+begin_example
Choose Madrigal context:
  symbol: madrigal-focus-context
  expression: focused call
  function: madrigal-focus-context
  buffer: madrigal-focus.el
  project: madrigal                    project metadata
#+end_example

Moving through candidates previews the range and summary. Selecting an entry
freezes it; cancellation makes no request. A region is offered exactly as
selected. The candidate list is stable for the session and is not recomputed
while navigating. Optional bracket-key navigation may later operate on that same
list, but must retain explicit confirmation.

** Programmatic API

Define context construction and selection as separate snapshot, discovery,
selection, and materialization operations.  Interactive wrappers translate a
prefix argument into either default selection or completion rather than
overloading instruction text.  Callers pass a materialized context to the
executor.

* Dynamic labels and target types

Scope labels are open and provider-defined.  The core does not translate them
into a closed vocabulary.  A provider may emit labels such as =symbol=,
=call_expression=, =defun=, =Org item=, =diff hunk=, or any more precise mode
concept.  Labels are presentation metadata.  The scorer consumes explicit
relevance signals rather than interpreting label names, and labels do not
determine representation or materialization rules.

The core has only three target types:

| Target      | Meaning                                                        |
|-------------+----------------------------------------------------------------|
| =document=    | A frozen range into a shared origin-buffer snapshot            |
| =project=     | Project metadata and a project-oriented action environment     |
| =session=     | Compact metadata about the running Emacs instance              |

Region, syntax nodes, things, lines, paragraphs, blocks, definitions, subtrees,
excerpts, and the accessible buffer are all document candidates with dynamic
labels.  The active region is a core document candidate with an
=active-region= origin and a stable =region= label because it records direct
user intent.  Providers may return overlapping candidates, multiple labels for
the same range, and candidates that are unrelated by containment.  Preserve these
alternatives in completion and relevance scoring.  Suppress only an exact
repeated candidate identity from the same provider; never deduplicate by range.

A project provider emits a metadata-only project candidate when project
discovery succeeds.  It serializes neither project files nor origin buffer text.
There is no project candidate when discovery fails.

The session candidate is always available and explicit-only.  It materializes
only compact Emacs metadata such as Emacs version, system type, and relevant
enabled features.  It contains no origin buffer identity, position, range,
selected text, project metadata, file path, or serialized editor contents.

* Capture architecture

** Candidate contract

A candidate carries a target, label, origin, relevance signals, confidence,
size, provider-context-limit status, and optional relationships to other
candidates.  Origin is either the core =active-region= origin or a discovery
provider and its provider-local identity.  A document target carries bounds
into one frozen origin-buffer snapshot and a point-containment flag; candidates
do not duplicate captured text.  Project and
session targets carry their respective metadata.  Materialization copies only
the selected document text, or the selected project or session metadata, into
the action context together with its label, provider, confidence, and
relationships.

** Discovery and policy

1. Freeze one origin-buffer text snapshot and its restriction, window, point,
   active region, optional project, and compact Emacs-session metadata before
   opening a minibuffer.
2. Create the exact active-region candidate when =use-region-p= succeeds and the
   captured region is non-empty.
3. Ask every applicable provider for candidates, including the session provider
   and the project provider only when a project exists.
4. Normalize and validate candidates while preserving overlapping ranges and
   labels.
5. Compute central relevance scores from provider-independent signals and
   provider hints, then establish a stable order for the session.
6. Select the active region when present; otherwise select the highest-scoring
   default-eligible candidate or show completion.
7. Materialize only the selected candidate into the action context.

Providers discover possibilities and supply relevance evidence; the central
policy chooses the default.  Candidate collection is additive, and one
provider's output never suppresses another provider's overlapping output.
Scoring has its own interface and remains independent of label vocabulary.
Useful signals include an active-region flag, point containment, range size,
exact versus heuristic discovery, provider-supplied specificity, provider
priority, and explicit-only status.  Scores and their explanations are
inspectable so the policy can evolve without changing candidate labels or
provider APIs.

** Providers

Providers are registered centrally with applicability predicates; they do not
install buffer-local mode hooks.  Every applicable provider runs for the frozen
snapshot.

Universal providers include conservative thing-at-point bounds, generic defun
bounds, logical line and paragraph, a point-centred excerpt, the accessible
buffer, and the session candidate.

The generic Tree-sitter provider starts at the named node at point and emits
every named ancestor through the syntax-tree root.  Each candidate uses the
node's reported type as its label and retains the ancestry relationship.  It
contains no language-specific node tables or classification code.  Nodes with
the same range remain distinct when Tree-sitter gives them distinct identities
or labels.

Lisp providers may additionally offer the atom, containing sexps, list forms,
and definition using Lisp-aware labels and bounds.  Narrow major-mode providers
may add richer candidates for Org, Magit, diff, compilation, Dired, tabulated
lists, message, and comint.  Their results augment the generic providers rather
than replacing them.  The project provider contributes one candidate only when
project discovery succeeds.

* Limits, privacy, and escalation

Choose a candidate before considering size. Never truncate either the
automatically selected context or a context explicitly selected by the user.
The sole exception is when the active provider exposes a known model input
context limit and the selected context exceeds that limit. In that case,
truncate only as needed to fit the known limit, mark the supplied context and
candidate metadata as provider-context-limit truncated, and make the truncation
visible before dispatch when selection is interactive. Do not invent a generic
text limit when the provider limit is unknown.

An =excerpt= is an independently discovered fallback candidate, not a shortened
version of another selected scope. Never represent an excerpt or a
provider-context-limit-truncated scope as a complete function, block, or
buffer. Preserve the full candidate locally for display and explicit selection.

The initial request contains only selected text and compact metadata. A session
selection instead contains only the compact Emacs-session metadata defined above.
Unselected candidates remain local. Provide an explicit read-only focused-action
expansion tool for agents. It accepts a candidate identity or a related
enclosing candidate and returns its label, target, range or metadata, text where
applicable, and a concise change summary. It does not automatically alter the
original action context, so tool history records every escalation.

* Dispatch policy

** madrigal-do

Without prefix, dispatch immediately using the highest-scoring default-eligible
context. With prefix, select scope first, then read or confirm instruction and
dispatch. The indicator always covers the frozen selected range.

** madrigal-do-dwim

Without prefix, request suggestions against the highest-scoring default-eligible
context. With prefix, select scope before the tool-free suggestion request. The
DWIM UI should show selected scope and annotate suggestions with confidence,
estimated impact, and reversibility.

Immediate actions are valid only for frozen selected context. Broad, destructive,
or project-impacting actions require preview/confirmation. Suggestions needing a
broader scope must not silently expand and run; offer the relevant candidate or
ask the user to rerun with prefix selection.

* Implementation plan

The implementation removes the current structural selector machinery,
=madrigal-focus-context-range-function=, its mode hooks, fixed character-limit
selection, project-only command family, and their associated customization
options.  The snapshot, candidate, selection, and materialization APIs defined
here are the only context system.

1. Define the new snapshot, candidate, selection, and materialized-context
   representations and their invariants.
2. Implement generic discovery, deterministic default selection, and context
   materialization.
3. Implement prefix completion, stable preview, cleanup, and cancellation.
4. Add high-value mode adapters through the new provider interface.
5. Add explicit expansion tooling.
6. Add DWIM scope requirements, confidence/impact labels, and review gates.
7. Delete tests for the removed selector and command APIs; replace them with
   tests of the new public behaviour and representation invariants.

* Tests and success criteria

Add table-driven ERT coverage for the active region's core origin, exactness,
and unconditional default precedence; range/text consistency;
point containment; stable scored ordering; preservation of overlapping and
same-range labels; complete generic Tree-sitter named-node ancestry without
language-specific configuration; additive Lisp and major-mode candidates;
default choices in Elisp, Tree-sitter, Org, Magit, diff, compilation, Dired,
tabulated-list, message, and comint fixtures; contexts below, at, and above
known provider model limits; no truncation when a provider limit is unknown;
visible provider-limit truncation during prefix selection; prefix
selection/preview cleanup/cancellation; stale origins; project candidate
presence and absence according to discovery; shared do/DWIM policy;
project-only privacy; session-target absence of origin, project, and document
context; and risky or scope-mismatched DWIM actions.

The design succeeds when users can predict default context without knowing mode
implementation, can deliberately choose any valid broader scope with a prefix,
and no longer need separate project commands.
